Part 1

AI-DLC v1이 밟은 순서

AI-DLC는 INCEPTION(무엇을 왜 만들지) → CONSTRUCTION(어떻게 만들지) → OPERATIONS(어떻게 배포·운영할지) 세 단계로 된 절차다. 이번 실행은 INCEPTION 안에서 아래 순서로 진행했고, Units Generation에서 멈췄다 — 코드는 한 줄도 쓰지 않았다.

실제로 판단 근거로 쓴 문서 읽었지만 이번 판단엔 안 쓴 문서 — 클릭하면 왜 안 썼는지 나온다
01

Workspace Detection

항상 실행

기존 코드가 있는지(브라운필드인지) 확인한다. enode는 Go 1.26으로 짜인 다섯 실행파일(mediator·enode· enodectl·runctl·iapadapter)짜리 브라운필드 프로젝트였다.

02

Reverse Engineering

조건부 · 브라운필드만

기존 코드를 읽고 아키텍처·컴포넌트·API 문서 아홉 개를 만드는 단계인데, 이번엔 다른 세션(v2 리뷰 워크스페이스)이 이미 만들어 둔 것을 그대로 옮겨왔다 — 코드가 그 스캔 시점과 같다는 것만 확인하고 다시 훑지 않았다.

03

Requirements Analysis

항상 실행

이미 쓰여 있던 요구사항 문서의 미정 표시 25개 중, 유닛을 나누는 경계에 실제로 영향을 주는 2개만 골라 질문했다(호스트 제어판 서버 위치, drain 노출 범위). 나머지 23개는 미정인 채로 기록만 하고 넘어갔다 — 다 물어보면 그것도 잘못이다.

답변 뒤에는 이 프로젝트의 정본 설계 저장소(enode-design)를 다시 대조해서, 이미 결정·구현된 것(GET /v1/nodes의 정확한 응답 모양)은 그 결정으로 교체하고, 새로 드러난 상호작용(drain을 무기한 걸면 대기열도 무기한 대기한다)은 미정 목록에 새로 추가했다.

04

User Stories

건너뜀

조건부 단계. 이번엔 건너뛰었다 — 대상이 외부 고객이 아니라 팀 자체 개발보드 함대를 관리하는 내부 도구고, 요구사항 문서 자체가 이미 기능마다 목적·수용 기준을 담고 있어 스토리로 다시 쓰면 같은 내용을 반복하게 됐다. 대신 "유닛-요구사항 절 매핑" 문서로 그 역할을 대신했다.

05

Workflow Planning

항상 실행

남은 단계 중 무엇을 실행할지 정하는 단계. 여기서 중요한 발견 하나 — 분석만 해봐도 internal/store와 internal/api가 세 기능(현황판·대기열·drain)에서 공통으로 겹친다는 게 이미 보였다. 이걸 유닛으로 어떻게 처리할지는 대신 정하지 않고 다음 단계로 넘겼다.

06

Application Design

조건부 · 이번엔 강제

새 컴포넌트·메서드 시그니처 수준의 설계. 원래는 "새 컴포넌트가 있을 때만" 실행하는 조건부 단계지만, 다음 단계(Units Generation)의 전제조건으로 못 박혀 있어 강제로 실행했다. 여기서 drain 정책이 Mediator에 닿는 새 엔드포인트(POST /v1/nodes/{id}/drain, 그 노드 자신만 호출 가능)처럼 실제 설계 결정 몇 개를 확정했다.

07

Units Generation

이번 실행의 목표 지점

요구사항 넷을 사람이 나눠 맡을 수 있는 작업 단위(유닛) 넷으로 쪼갠다. 파일이 겹치는지는 아무도 시키지 않았는데 앞선 단계에서 이미 관측한 사실을 근거로 스스로 확인했다 — 아래 "유닛을 이렇게 나눈 이유"에서 자세히 다룬다.

08

Construction

이번 라운드 아님

여기서부터가 실제 코드를 쓰는 단계다. 이번 실행 지시(START.md)가 "Units Generation까지, 코드는 한 줄도 쓰지 않는다"로 못 박아 뒀으므로 멈췄다. 팀이 유닛을 나눠 맡으면 그때부터 시작되는 구간이다.

Part 2

enode 용어 사전

회의에서 이 단어들이 그냥 나온다. 아는 셈 치고 넘어가지 않아도 되게 하나씩 풀어 썼다.

시스템을 이루는 것들 component

enode 왜 이 이름인가
이 프로젝트 전체의 이름이자, 자원이 있는 기계(개발보드가 꽂힌 PC 등)에 상주하는 노드 데몬 프로세스의 이름이기도 하다. "부재중인 담당자의 대리인" — 개발보드처럼 복제할 수 없는 자원에 AI가 대신 접근하게 하는 것이 이 프로젝트의 존재 이유다.
Mediator
중앙 서버 하나. 상태(누가 무엇을 하고 있나)를 유일하게 소유한다. 매칭·임대·시퀀싱을 하고 결과를 봉인한다. PostgreSQL에 저장한다.
노드 node
광고를 보내는 기계 한 대. node_id로 식별한다. 노드는 절대 먼저 듣지 않는다 — 항상 자기가 Mediator로 연결을 건다(방화벽 뒤 개발보드가 아무 설정 없이 함대에 들어올 수 있는 이유).
enodectl
한 기계에 있는 enode를 로컬에서 관리하는 CLI — status·start·stop·logs. 오늘은 HTTP를 전혀 안 쓰는 순수 로컬 도구다. 이번 기능(호스트 제어판)이 여기 첫 HTTP 서버를 얹는다.
runctl
사람이 쓰는 CLI. 무상태. Run을 제출하고 상태를 조회하고 취소한다.
하네스 harness
노드가 실제로 실행하는 AI 실행기 — 지금은 claude CLI 하나뿐이다. enode가 이걸 실행하는 유일한 지점을 갖고 있다.

일이 흘러가는 방식 lifecycle

Run
사용자가 제출한 작업 실행 하나. CREATED → RESOLVING → ALLOCATING → RUNNING → VERIFYING → SUCCEEDED/FAILED 상태를 지나간다.
계약 contract
Run이 무엇을 할지 선언한 문서. 단계(step)들과 그 사이의 의존(needs)을 담는다.
광고 advertise
노드가 "나는 무엇을 할 수 있다"를 스스로 알리는 것. 매번 전부를 다시 보내고, 만료된다. 소유자가 편집할 수 없다 — 다음 광고가 덮어버리기 때문이다.
임대 lease
Mediator가 노드 하나를 어느 Run에 배타적으로 묶는 것. 노드 하나엔 임대가 최대 하나뿐이다. 광고와 달리 사람이 정하고, 만료되지 않는다 — 이 차이가 이번에 만드는 drain 기능의 핵심 축이다.
claim
노드가 "내가 할 일 있어?"라고 Mediator에 롱폴(길게 붙잡는 요청)로 묻는 것. 저장소에서 유일하게 비멱등(같은 요청을 두 번 하면 결과가 달라짐)인 지점이다.
Record
Run이 끝나면 파일시스템에 봉인되는 실행 기록. 봉인되면 고칠 수도 지울 수도 없다.

이번에 새로 배우는 것 이번 라운드

drain
노드 소유자가 "내 자원 돌려줘"라고 말하는 것. 새 임대만 막는 graceful 모드와, 다음 단계 경계에서 강제로 놓는 at-boundary 모드 둘이 있다. Run을 죽이지 않는다는 게 핵심 — 그 점이 "선점(preemption, 이번엔 안 만듦)"과 갈리는 지점이다.
소유자 principal
노드를 함대에 내놓은 사람. 지금까지는 이 값이 장부에 기록만 되고 아무 데도 쓰이지 않았다 — 이번 기능이 처음으로 이걸 쓰는 기능이다.
QUEUED
새로 생기는 Run 상태. 지금은 자원이 다 차 있으면(409) 즉시 실패(FAILED)로 죽는데, 이번 기능은 그 대신 대기시켰다가 자원이 풀리면 자동으로 재시도하게 한다.
운용 관측 operational observation
운영자가 지금 함대에 무슨 일이 있는지 보는 것 — GET /v1/nodes가 담당한다. 배정 판정이 아니다 — 이 응답을 보고 "이 노드가 비어 있다"고 믿고 행동하면 그 사이 다른 Run이 채갈 수 있다. 실제 배정 가능 여부는 항상 Mediator의 매칭 함수만 안다.
INVARIANTS
정본 설계 저장소(enode-design)가 정한, 절대 깨면 안 되는 규칙 목록. 예를 들어 I1은 "노드 하나는 동시에 임대 하나"고, I4는 "봉인된 Record는 못 고친다". 이번 기능들은 전부 이 규칙을 건드리지 않는 선에서 설계됐다.
ADR
Architecture Decision Record — "왜 이렇게 정했나"를 적어두는 문서. 이번에 세 개(ADR-063 drain, ADR-064 대기열, ADR-065 운용 관측)를 대조했다. 앞 둘은 아직 초안(미결)이고, 마지막은 이미 결정되고 구현까지 됐다.
Part 3 · 회의에서 쓸 내용

유닛을 이렇게 나눈 이유

요구사항 넷이 그대로 유닛 넷이 됐다. 그런데 그냥 넷으로 나눈 게 아니라, 어느 파일이 겹치는지를 스스로 찾아서 그 위에 병합 순서 권고를 얹었다 — 아무도 "파일 겹침을 확인해라"라고 시키지 않았는데도. 여기가 팀장이 궁금해할 지점이다.

U1

중앙 현황판

requirements.md 3.1.2

함대 전체가 지금 뭘 하는지 한 화면에서 본다. GET /v1/runs· GET /v1/nodes 신규.

의존: 없음 — 바로 시작 가능. 대기열(U2)과 서로를 완성시켜준다.
담당 후보 — 대시보드 계열
U2

대기열

requirements.md 3.2.2

자원이 꽉 찼을 때 죽는 대신 기다린다. 409 → QUEUED, FIFO 하나로 순서를 정한다.

의존: U1과 상호 의존 — 둘 다 끝나야 "대기 Run이 목록에 뜬다"가 참이 된다.
U3

drain

requirements.md 3.2.1

소유자가 자기 자원을 돌려받는다. 정책 저장 + 매칭 제외 + 노드 전용 신규 엔드포인트.

의존: 없음 — 바로 시작 가능. 대기열(U2)과 동작으로 얽힌다(코드 의존은 아님).
U4

호스트 제어판

requirements.md 3.1.1

노드 소유자가 자기 기계에서 enode를 보고 통제한다. enodectl에 첫 HTTP 서버가 생긴다.

의존: U1·U3에 진짜로 의존 — 그 둘의 엔드포인트가 서야 완주(수용 기준 통과)할 수 있다.
담당 후보 — 대시보드 계열

어느 파일에서 실제로 부딪히나

패키지 이름만 보면 안 와닿을 수 있어서 파일 단위로 짚었다. internal/api/api.go는 파일 하나에 API 라우트 15개가 전부 등록돼 있는 구조다 — 세 유닛이 여기 동시에 손을 대면 코드 리뷰나 병합 순서를 정하지 않는 이상 반드시 부딪힌다.

파일은 안 겹치는데 동작으로 얽히는 것 하나

drain(U3)을 무기한으로 걸어두면, 그 노드를 기다리는 대기열(U2)의 Run도 무기한 대기하게 된다 — 이건 정본 설계 문서(ADR-064)가 짚은 내용이다. 코드 의존은 아니라서 유닛은 따로 개발해도 되지만, 통합 테스트는 반드시 같이 봐야 한다. 둘 다 각자 수용 기준을 통과해도 이 상호작용은 저절로 검증되지 않는다.

Part 4 · 참고 구현

이미 있는 대시보드 화면 — 화면별로 뜯어보기

다른 클론(enode-work/enode, 브랜치 feat/runaway-dashboard-observation, 아직 원격 main에 안 올라간 상태)에 Python 표준 라이브러리만으로 짠 참고 대시보드가 이미 있다. 우리 U1·U4가 최종적으로 Go로 만들 것과 기술 스택은 다르지만(이건 Python 서버가 Mediator를 대신 호출하는 방식), 화면 구성과 "무엇을 보여줘야 하는가"는 그대로 참고할 수 있다.

이 스크린샷들은 Mediator가 꺼진 상태에서 찍혔다 — WinError 10061(연결 거부)이 곳곳에 보이는 이유다. 그래서 데이터는 비어 있지만, 화면 구조와 라벨(LIVE·MOCK·CONFIG 같은 출처 표시)은 실제 그대로다.

요약과 결론

인과 사슬은 한 방향으로 이어진다. 입력은 완전히 같았다(md5 동일) → Requirements Analysis에서 범위·깊이·확장 판단이 갈렸다 (v1-run-01만 START.md 없이 진행, 스스로 "Comprehensive"를 택함) → 그 판단이 User Stories 실행 여부와 스토리 개수를 갈랐다(0 · 10 · 25) → 그것이 Application Design의 컴포넌트 표기 범위와 UI 분리 여부를 갈랐다 → 최종적으로 Units Generation의 분할 축과 개수(4 · 10 · 7)로 나타났다. 유닛 개수 차이는 원인이 아니라 결과다 — 진짜 갈림은 훨씬 앞, 첫 게이트 질문에서 이미 났다.

prep/GOALS.md와 START.md §5는 이미 이렇게 경고해 뒀다 — "v1 에는 협업 지원이 없다 ... 유닛이 겹치면 사람이 그냥 부딪힌다." 세 실행의 유닛 개수가 다르다는 것 자체가 그 경고의 실측 증거다. 넷의 unit-of-work.md를 이어붙여서 그대로 팀원 4명에게 나눠줄 수 없다 — 세 실행이 이미 서로 다른 축(기능 1:1 · 기능+선행 이동 · 바닥+화면분리)으로 세계를 나눴기 때문이다.

팀 종합 회의에서 할 일은 "누구 유닛 개수가 맞았나"를 가리는 게 아니라, Requirements Analysis 게이트로 다시 돌아가 범위(필수 넷인가 여섯인가)와 확장 opt-in을 팀 전체가 하나로 맞추고, 그 다음에야 Part 3의 파일 겹침 표처럼 분할 축 하나를 골라 유닛을 다시 긋는 것이다. 축을 먼저 통일하지 않으면 네 사람의 "완료"가 서로 다른 경계를 가리키게 된다.
